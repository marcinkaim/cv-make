# Technical Specification: CV Make (`cv-make`)

This document constitutes the definitive technical specification for **CV Make** (`cv-make`), an automated, containerized Command-Line Interface (CLI) utility engineered to transform Markdown-formatted curriculum vitae documents into high-quality, ATS-compliant PDF files. It serves as an architectural blueprint, outlining functional requirements, user interaction models, DTP rendering rules, container orchestration strategies, and distribution workflows.

---

## 1. General Overview & Requirements

Section 1 defines the foundational parameters governing the `cv-make` project. It establishes the high-level objectives, enumerates explicit functional and non-functional requirements, defines the environment boundaries (Debian 13 Trixie runtime within Podman/Docker), and outlines licensing compliance for Open Source distribution.

### 1.1 Project Objectives & Scope

The primary objective of **CV Make** is to eliminate the friction between plain-text content management and professional document typesetting for software engineers and technical platform professionals. By decoupling raw Markdown content from visual presentation rules, `cv-make` enables users to maintain a single source of truth (`CV.md`) while deterministically generating publication-ready PDF documents.

#### Core Problem Statement
Traditional word processors and visual CV builders introduce formatting inconsistencies, pollute text streams with invisible metadata, and often fail Applicant Tracking System (ATS) parsing checks. Conversely, raw LaTeX toolchains introduce heavy host-level dependency footprints (often exceeding 2 GB) and steep syntax overhead for simple structural adjustments.

#### Scope & Design Principles
`cv-make` bridges this gap through four core design principles:

1. **Strict Execution Isolation & Reproducibility:**
   All compilation dependencies—including Python 3 runtimes, the WeasyPrint DTP layout engine, parsing libraries, and system font packages (`fonts-ibm-plex`)—are encapsulated within an immutable container image based on `debian:trixie-slim`. Document generation produces byte-identical visual layouts regardless of the host operating system.

2. **ATS-First Engineering:**
   The output PDF maintains an un-rasterized, semantic Unicode text stream. Document structures generated by `cv-make` preserve natural reading order, hyperlinks, and layout geometry, ensuring seamless parsing by automated recruitment platforms (e.g., Lever, Greenhouse, Workday).

3. **Decoupled Presentation via Cascading Stylesheets:**
   Structural transformation (Markdown to semantic HTML5) is fully isolated from visual styling (CSS Paged Media). The parser attaches semantic attributes and predictable element IDs, allowing visual layout, typography, line spacing, and color schemes to be customized entirely via CSS without modifying source application code.

4. **Zero-Overhead Host Integration:**
   The utility operates via a lightweight host wrapper script installed in the user's local path (`~/.local/bin` or `%USERPROFILE%\.local\bin`). It requires no administrative (`root`) privileges and depends strictly on the presence of a container runtime (Podman or Docker).

### 1.2 Functional Requirements

Section 1.2 specifies the functional capabilities required of the `cv-make` tool. These requirements govern command-line invocation, stream management, Markdown structural mapping, layout rules, hyperlink handling, and presentation decoupling.

#### Requirement 1: Command-Line Interface & Parameter Parsing

* **CLI Parameter Map:** The utility shall accept arguments for the input Markdown document, an optional profile photograph, optional custom CSS stylesheets, and the output PDF destination file path.
* **Syntax Signature:**
   ```bash
   cv-make [INPUT.md] [--photo IMAGE_PATH] [--style STYLESHEET.css ...] [--out OUTPUT.pdf]
   ```
* **Multiple Stylesheet Ingestion:** The CLI shall accept multiple `--style` flag invocations. Stylesheets shall be injected in the exact order declared on the command line.

#### Requirement 2: Stream Processing & Pipeline Integration

* **Standard Input (STDIN):** If no input file path is provided (or if `-` is specified), `cv-make` shall read the source Markdown content directly from `STDIN`.
* **Standard Output (STDOUT):** If no output file path (or `--out -`) is specified, `cv-make` shall write the compiled binary PDF document directly to `STDOUT`.
* **Stream Discipline:** All operational logs, diagnostic messages, container engine auto-detection outputs, and progress indicators shall be written exclusively to `STDERR` (`>&2`). `STDOUT` must remain unpolluted to guarantee binary PDF validity when redirected in Unix shell pipelines (`cat CV.md | cv-make > output.pdf`).

#### Requirement 3: Section Heading Mapping Hierarchy

The document structure shall map strictly to a 4-tier HTML heading hierarchy:

* **H1 (`#`):** Main Title / Candidate Name.
* **H2 (`##`):** Primary CV Sections (e.g., `PROFILE SUMMARY`, `KEY SKILLS`, `WORK EXPERIENCE`, `EDUCATION`).
* **H3 (`###`):** Standard Subsections (e.g., recent employer entries, university degrees).
* **H4 (`####`):** Compact Subsections (e.g., historical employer entries prior to 2020).

#### Requirement 4: Compact Experience Formatting Engine

* **H4 Hierarchy compacting:** Any subsection marked with an `H4` (`####`) heading shall be rendered in a compact layout mode.
* **CSS-Driven Compacting:** The Python preprocessor shall wrap `H4` elements and their sibling nodes in a semantic container (`<div class="entry-compact">`). Visual compression (reduced margins, smaller font size, tighter line heights) is applied entirely via CSS without hardcoded section-name checks in the parser code.

#### Requirement 5: Markdown Inline Styling & List Formatting

* **Inline Elements:** Bold (`**text**`), italic (`*text*`), and inline code formatting shall map directly to equivalent HTML5 inline tags (`<strong>`, `<em>`, `<code>`).
* **List Hierarchies:** Single-level and multi-level nested unordered (`<ul>`/`<li>`) and ordered (`<ol>`/`<li>`) bullet lists shall map directly to native nested HTML list structures, preserving visual indentation and list markers.

#### Requirement 6 & 7: Universal Line Splitting & Right-Aligned Date Engine

* **Single-Purpose Pipe Operator (`|`):** The pipe symbol (`|`) is strictly reserved as an alignment separator across all CV sections.
* **Flexbox Transformation Rule:** Any Markdown header (`H3`/`H4`) or standalone paragraph containing a pipe (`|`) symbol shall be parsed into a 2-column flexbox container:
   ```html
   <h3 class="flex-line">
   <span class="line-left">Company Inc.</span>
   <span class="line-right">01.2023 – 03.2024</span>
   </h3>
   ```
* **Unification:** This mechanism applies identically to recent work experience, historical experience, and education sections (`### University Name | 2004 – 2010`). The pipe symbol is stripped from output rendering, and the post-pipe text is aligned flush right (`justify-content: space-between`).

#### Requirement 8: Main Header Block & Profile Photo Layout

* **Two-Column Grid Structure:** The top section containing candidate identity and contact metadata shall be generated as a 2-column container (`<header class="header-main">`).
* **Left Column:** Contains H1 candidate name, professional title, location, language levels, and interactive contact/profile links.
* **Right Column:** Contains the portrait photograph supplied via `--photo`. The container automatically applies fixed width and aspect ratio constraints. If no photo argument is supplied, the left column automatically expands to fill 100% of the header width.

#### Requirement 9: Interactive Hyperlink Processing

* **Markdown Notation:** Hyperlinks shall be recognized from standard Markdown link syntax, such as `[https://github.com/username](https://github.com/username)` or `[LinkedIn Profile](https://linkedin.com/in/username)`.
* **URI Annotations:** Links shall be rendered as native URI annotations within the PDF document, preserving clickability, visual link highlighting, and full navigation support for both human readers and ATS software.

#### Requirement 10: Structural Abstraction, Multi-Level Slugification & CSS Cascade Engine

* **Minimal Structural Awareness:** The Python preprocessor remains agnostic to specific section titles, handling layout and DOM enrichment strictly via heading hierarchy levels (H1 through H4) and generic pipe syntax.
* **Automated Multi-Level Section Wrapping & Slugification:** Every section and subsection at all heading levels (H1, H2, H3, and H4) shall be encapsulated within semantic containers (`<section class="cv-section level-{n}" id="{slug}" data-title="{title}">`). The `id` slug is algorithmically generated across all levels by:
    1. Converting heading text to lowercase.
    2. Replacing all non-alphanumeric characters with hyphens (`-`).
    3. Collapsing consecutive hyphens (`--`) into a single hyphen (`-`).
    4. Trimming leading and trailing hyphens.
        *(Example: `### Independent R&D / Open Source Projects | 08.2025 – present` -> `id="independent-r-d-open-source-projects-08-2025-present"`)*.
* **Cascading Stylesheet Inheritance:** The document compilation shall **always** load the embedded base stylesheet (`default.css`) first. Any custom user stylesheets provided via `--style` flags shall be injected sequentially afterward, enabling users to target specific section IDs at any structural depth and override default styling rules, fonts, colors, or layout properties via standard CSS cascade order.

### 1.3 Non-Functional Requirements

Section 1.3 details the non-functional software quality attributes, execution boundaries, OS compatibility matrix, rootless installation mechanics, and licensing parameters.

#### Requirement 11: Isolated Containerized Runtime Environment
- **Container Sandbox:** All compilation, pre-processing, and PDF rendering tasks must execute exclusively inside an isolated container sandbox (Podman or Docker).
- **Host Cleanliness:** The host operating system requires no Python, WeasyPrint, or DTP software dependencies; only a compatible container runtime engine is mandated.

#### Requirement 12: Base OS & Environment Boundaries
- **Primary OS Target:** Debian 13 Trixie (Linux) serves as the primary development and base container OS image (`debian:trixie-slim`).
- **Secondary OS Target:** Full interoperability with Windows 10/11 environments via PowerShell scripts and CMD wrappers.

#### Requirement 13: Universal Scripted Installers
- **Linux Installer:** `install_linux.sh` (POSIX Bash script) providing rootless environment configuration.
- **Windows Installer:** `install_win.ps1` (PowerShell script) managing Windows user environment integration.
- **Package Manager Agnosticism:** Installation bypasses distribution-specific packages (`.deb`, `.rpm`, `.msi`), executing purely via scriptable container pulls and local binary wrapping.

#### Requirement 14: Local Rootless Installation & Self-Healing Wrapper
- **Rootless Installation:** The installation executes entirely within user space (writing binaries to `~/.local/bin` on Linux and `%USERPROFILE%\.local\bin` on Windows). No administrative/root privileges are required.
- **Self-Healing Mechanics:** The CLI wrapper script dynamically inspects local container storage. If the container image (`cv-make:latest` or GHCR image) is missing (e.g., deleted via `podman system prune`), the wrapper automatically pulls the required image on demand prior to document generation, writing progress logs strictly to `STDERR`.

#### Requirement 15: Multi-Channel Uninstallation Architecture
- **CLI Flag Uninstallation:** Execution of `cv-make --uninstall` purges the container image from local storage and removes executable wrappers. On Windows, file-locking restrictions are bypassed via an asynchronous, detached background cleanup process.
- **Installer Uninstallation Flag:** Both `install_linux.sh --uninstall` and `install_win.ps1 -Uninstall` provide explicit script-driven teardown capabilities.
- **Windows OS Control Panel Integration:** The Windows installer registers an uninstallation entry within the user-level Windows Registry (`HKCU:\Software\Microsoft\Windows\CurrentVersion\Uninstall\cv-make`), allowing users to remove the software natively via the Windows Settings / "Apps & Features" GUI without administrative rights.

#### Requirement 16: Minimal System Prerequisites
- **Host Prerequisites:** The host system requires only a functional container engine (Podman or Docker) and a native shell interpreter (Bash for Linux, PowerShell 5.1+ for Windows).

#### Requirement 17 & 18: Project Identity & Binary Naming
- **Binary Identity:** Executable wrapper named `cv-make` (Linux) or `cv-make.cmd` (Windows).
- **Project Identity:** Official project naming designated as **CV Make**.

#### Licensing & Compliance

* Source Code License: Released under the GNU General Public License v3.0 (GPLv3).
* Font Distribution & Licensing: System fonts installed inside the container environment are provided by standard Debian repository packages (adhering to Debian Free Software Guidelines). Font embedding during PDF compilation carries no licensing restrictions or copyleft obligations on the generated CV documents.
* ATS Parsing Guarantee: Output PDF files must contain un-rasterized vector text streams fully readable by standard text extraction tools (pdftotext).

## 2. CLI Specification & User Experience

Section 2 defines the command-line interface (CLI) behavior, parameter resolution logic, standard stream management, container engine auto-detection, and local lifecycle workflows for `cv-make`. It establishes the operational interface exposed to end-users across Linux and Windows execution environments.

### 2.1 Interface & Parameter Handling

The `cv-make` utility operates as an intuitive, POSIX-compliant command-line tool. It supports both standard file-path invocations and streaming Unix pipeline operations while maintaining strict isolation of diagnostic output from binary data streams.

#### Command-Line Signature

```bash
cv-make [INPUT.md] [--photo IMAGE_PATH] [--style STYLESHEET.css ...] [--out OUTPUT.pdf] [--uninstall] [--help]
```

#### Parameter Map & Arguments Definition

* **`INPUT.md` (Positional Argument, Optional):**
   * Specifies the source Markdown document file path.
   * If omitted, or if explicit `-` is passed, `cv-make` reads the source Markdown text directly from `STDIN`.
* **`--photo`, `-p` (Named Option, Optional):**
   * Specifies the local file path to the candidate's portrait photograph (supported formats: JPEG, PNG, WebP).
   * When provided, the top header layout renders a 2-column grid with an auto-fitted photo container on the right.
   * If omitted, the contact information block in the left column automatically expands to fill 100% of the header width.
* **`--style`, `-s` (Named Option, Optional, Repeatable):**
   * Specifies the path to a custom CSS stylesheet file to override default visual presentation rules.
* **Repeatability & Cascade Order:** This option may be declared multiple times on a single invocation (e.g., `--style theme.css --style print-adjustments.css`). Custom stylesheets are appended sequentially after the embedded base stylesheet (`default.css`), adhering strictly to standard CSS cascade priority rules.
* **`--out`, `-o` (Named Option, Optional):**
   * Specifies the destination file path for the compiled output PDF document.
   * If omitted, or if explicit `-` is passed (`--out -`), `cv-make` writes the binary PDF stream directly to `STDOUT`.
* **`--uninstall` (Flag Option, Optional):**
   * Triggers the automated uninstallation workflow, purging the container image from local storage and unlinking the local wrapper executable scripts.
* **`--help`, `-h` (Flag Option, Optional):**
   * Displays command-line usage syntax, available parameters, and version information, then exits immediately with status code `0`.

#### Standard Stream Processing & Pipeline Integration

* **Input Stream Processing (`STDIN`):** When operating in stream mode (`cat CV.md | cv-make > cv.pdf`), the preprocessor buffers input from `STDIN` until EOF before initiating AST transformation and HTML generation.
* **Output Stream Processing (`STDOUT`):** When outputting to `STDOUT`, `cv-make` emits the raw binary PDF stream produced by WeasyPrint.
* **Strict Logging Discipline (`STDERR`):**
   * All diagnostic outputs, image-pull progress indicators, container engine auto-detection notices, warnings, and error messages **must be directed exclusively to `STDERR` (`>&2`)**.
   * Writing non-binary plain-text log messages to `STDOUT` during stream compilation is strictly prohibited, as it corrupts the binary structure of the generated PDF file.

#### Custom Stylesheet Ingestion Logic

1. The containerized execution environment always loads the built-in `/app/styles/default.css` stylesheet first.
2. For each custom CSS file declared via the `--style` parameter, the host wrapper mounts the specified stylesheet file into the container workspace.
3. The preprocessor dynamically injects `<link rel="stylesheet">` tags into the intermediate HTML DOM in the exact order specified on the command line:
   ```html
   <link rel="stylesheet" href="default.css">
   <link rel="stylesheet" href="user_style1.css">
   <link rel="stylesheet" href="user_style2.css">
   ```
4. This mechanism grants users complete freedom to override default fonts, colors, section spacing, or pipe-alignment (`.flex-line`) behaviors using custom CSS rules without modifying core application code.

### 2.2 Host Environment & Container Engine Auto-Detection

To maintain zero-overhead host integration and universal compatibility across platforms, `cv-make` relies entirely on external container engines. The wrapper executable dynamically identifies, validates, and selects an active container runtime (Podman or Docker) on the host system prior to initiating document compilation.

#### Engine Discovery & Validation Algorithm

The auto-detection logic prioritizes rootless container execution, favoring Podman over Docker. Simple existence checks of binaries in the system `PATH` are insufficient; the wrapper must verify that the engine is active, responsive, and accessible without elevated administrative permissions.

The selection algorithm operates in the following strict precedence:

1. **Podman Validation:**
   * The wrapper checks for the executable `podman` in the system `PATH`.
   * If present, it executes `podman info` to verify runtime health and rootless daemon status.
   * If `podman info` exits with status code `0`, **Podman** is selected as the active engine.
2. **Docker Fallback Validation:**
   * If Podman is missing or unresponsive, the wrapper checks for the executable `docker` in the system `PATH`.
   * If present, it executes `docker info` to confirm that the Docker daemon (`dockerd`) is running and that the current user has permission to communicate with the Docker socket (e.g., membership in the `docker` group).
   * If `docker info` exits with status code `0`, **Docker** is selected as the active engine.
3. **Detection Failure:**
   * If neither engine returns a valid status code, execution halts immediately.

```
              ┌─────────────────────────────┐
              │ Start Container Auto-Detect │
              └──────────────┬──────────────┘
                             │
                             ▼
               /─────────────────────────\
              < Is `podman info` valid?   >──YES──► [ Select Engine: podman ]
               \─────────────────────────/
                             │ NO
                             ▼
               /─────────────────────────\
              <  Is `docker info` valid?  >──YES──► [ Select Engine: docker ]
               \─────────────────────────/
                             │ NO
                             ▼
              ┌─────────────────────────────┐
              │  Emit Error to STDERR       │
              │  Exit with Status Code 1    │
              └─────────────────────────────┘

```

#### Failure Handling & User Diagnostics

If engine auto-detection fails, `cv-make` outputs a formatted error message strictly to `STDERR` and terminates with exit code `1`. The message explicitly informs the user of missing runtime requirements:

```text
[ERROR] No active container engine detected!
cv-make requires a functional Podman or Docker environment.
Please ensure that Podman or Docker Desktop is installed, running, and accessible by the current user.
```

#### Container Invocation Parameters & Targeted Mounting

Once an engine is selected, the host wrapper invokes the container image (`ghcr.io/<user>/cv-make:latest` or local `cv-make:latest`) using a streaming execution model with targeted asset mounts:

* **Interactive Execution (`-i`):** Attaches host standard input to the container process, enabling direct Markdown stream piping (`podman run -i ... < INPUT.md`).
* **Ephemeral Container (`--rm`):** Automatically purges the container filesystem layer upon process termination, preventing container accumulation on the host.
* **Targeted Asset Mounts (`-v`):** Mounts only explicitly supplied asset files (`--photo` or `--style`) as read-only volumes into container-isolated temporary paths (`/tmp/assets/...:ro,z`). The wrapper avoids mounting the entire working directory, guaranteeing least-privilege file access and host filesystem immunity.

### 2.3 Installation & Wrapper Lifecycle

The installation and lifecycle management of `cv-make` are designed around a zero-privilege, rootless paradigm. Installation executes entirely in user space, requiring no administrative or root privileges, while ensuring host system cleanliness and seamless OS-level integration across Linux and Windows environments.

#### Scripted Installer Architecture

The repository provides two universal installer scripts located at the repository root:
* **`install_linux.sh` (Linux / POSIX Bash):** Orchestrates wrapper installation and shell environment PATH configuration for Linux desktops and servers (optimized for Debian 13 Trixie).
* **`install_win.ps1` (Windows PowerShell):** Orchestrates wrapper creation, User Registry registration, and Windows environment variable integration for Windows 10/11.

#### Installation Execution Workflow
When an installer script is executed, it performs the following sequential lifecycle steps:

1. **Pre-flight Container Engine Verification:**
   * The installer verifies the presence of an active, functional container engine (Podman or Docker) using the auto-detection algorithm defined in Section 2.2.
   * If no responsive container engine is detected, installation halts immediately, emitting an error diagnostic to `STDERR`.

2. **Container Image Purge & Fresh Pull Enforcement:**
   * To guarantee that the local environment is updated to the latest release and to prevent stale image caching issues, the installer checks local container storage for existing `cv-make:latest` or `ghcr.io/<user>/cv-make:latest` images.
   * If an existing image is found, the installer forcefully purges it (`podman rmi -f`).
   * The installer then pulls a fresh container image directly from the public GitHub Container Registry (`podman pull ghcr.io/<user>/cv-make:latest`).

3. **Local Wrapper Executable Creation:**
   * **Linux Environment (`~/.local/bin/cv-make`):**
      * Generates an executable Bash wrapper script in the user's local binary directory (`~/.local/bin/cv-make`).
      * Grants execution permissions (`chmod +x ~/.local/bin/cv-make`).
      * Ensures `~/.local/bin` is present in the user's `PATH` environment variable (appending export statements to `~/.bashrc` or `~/.zshrc` if necessary).
   * **Windows Environment (`%USERPROFILE%\.local\bin\cv-make.cmd`):**
      * Creates the target local directory `%USERPROFILE%\.local\bin` if it does not exist.
      * Generates a Windows Command batch wrapper (`cv-make.cmd`) that invokes the container engine and proxies CLI arguments.
      * Appends `%USERPROFILE%\.local\bin` to the User Environment `PATH` variable using PowerShell `[Environment]::SetEnvironmentVariable` (targeting the `User` scope, requiring no elevation).

4. **Windows Rootless Control Panel Registry Registration:**
   * To provide native Windows Desktop UX without requiring Administrator rights, `install_win.ps1` registers `CV Make` within the user-level Windows Registry hive:
     `HKCU:\Software\Microsoft\Windows\CurrentVersion\Uninstall\cv-make`
   * The script populates the following registry string values:
      * `DisplayName` = `"CV Make"`
      * `DisplayVersion` = `"1.0.0"`
      * `Publisher` = `"CV Make Project"`
      * `UninstallString` = `"powershell.exe -ExecutionPolicy Bypass -File \"<path_to_install_win.ps1>\" -Uninstall"`
      * `NoModify` = `1`
      * `NoRepair` = `1`
   * **Impact:** `CV Make` appears natively in the Windows Settings GUI under **Apps > Installed Apps** (or "Add/Remove Programs"). Clicking "Uninstall" in the Windows GUI triggers the rootless PowerShell teardown script without prompting for UAC administrator elevation.

#### Self-Healing Runtime Mechanics

To protect against accidental image loss (e.g., when a developer runs `podman system prune -a` or `docker system prune -a` to reclaim disk space), the host wrapper script implements a self-healing mechanism:

1. **Pre-Execution Cache Inspection:** Upon every invocation of `cv-make`, the wrapper performs a lightweight, local inspection query (`podman image exists ghcr.io/<user>/cv-make:latest`).
2. **On-Demand Image Recovery:** If the container image is missing from local storage, the wrapper pauses compilation, outputs a notice to `STDERR` (`[cv-make] Image missing. Restoring from GHCR...`), and automatically executes `podman pull ghcr.io/<user>/cv-make:latest`.
3. **Execution Continuity:** Once restored, document compilation proceeds immediately without user intervention, ensuring high availability and zero-maintenance CLI operations.

### 2.4 Uninstallation Procedure

The uninstallation procedure for `cv-make` is designed to be complete, non-intrusive, and fully executable without requiring elevated administrative privileges. It guarantees a complete teardown of local binaries, container images, registry entries, and OS-level application registrations across Linux and Windows platforms.

#### Uninstallation Entry Points & Triggers

Uninstallation can be initiated through three distinct channels:
1. **CLI Flag Invocation (`cv-make --uninstall`):** Direct command-line invocation by the end-user.
2. **Installer Teardown Flag (`install_linux.sh --uninstall` / `install_win.ps1 -Uninstall`):** Scripted uninstallation using the original repository installer scripts.
3. **Windows System Settings GUI:** Native removal triggered via Windows **Settings > Apps > Installed Apps** (or Add/Remove Programs), which executes the registered rootless uninstallation script in the background.

#### Teardown Execution Sequence

Regardless of the initiation channel, the uninstallation sequence performs the following steps:
1. **Active Container Runtime Detection:**
   * Evaluates system availability of Podman or Docker using the auto-detection algorithm defined in Section 2.2.
2. **Container Image Purge:**
   * Queries local container storage for `ghcr.io/<user>/cv-make:latest` and local `cv-make:latest` images.
   * Forcefully purges image layers using `$ENGINE rmi -f <image_id>` to reclaim host disk space.
3. **User-Space Binary Teardown:**
   * **Linux Environment:** Unlinks and deletes the wrapper executable at `~/.local/bin/cv-make`.
   * **Windows Environment:** Deletes the batch wrapper at `%USERPROFILE%\.local\bin\cv-make.cmd`.
4. **Windows Registry Entry Cleanup:**
   * Removes the registry key hive at `HKCU:\Software\Microsoft\Windows\CurrentVersion\Uninstall\cv-make`.
   * Instantly refreshes the Windows Installed Apps list without requiring system restarts or Administrator elevation.

#### Asynchronous Windows File-Lock Bypass Mechanism

On Windows operating systems, the Command Prompt (`cmd.exe`) and PowerShell interpreters place an exclusive OS-level file lock on active batch/script files during execution. Consequently, running `cv-make --uninstall` directly inside `cv-make.cmd` would trigger a file access error if the script attempted to delete itself while running.

To overcome this constraint without requiring administrative elevation, the Windows wrapper implements an asynchronous detached self-deletion routine:
1. **Resource Teardown Phase:** The wrapper removes the container image from Podman/Docker storage and purges the User Registry keys.
2. **Detached Process Spawning:** Immediately prior to exiting, the wrapper spawns an independent, background subshell process configured with a brief delay:
   ```cmd
   start /b "" cmd /c "timeout /t 2 >nul & del /f /q "%~f0""
   ```
3. **Termination & Self-Deletion:** The primary `cv-make.cmd` process terminates instantly, releasing the OS file lock. Two seconds later, the background process executes `del /f /q`, successfully removing `cv-make.cmd` from `%USERPROFILE%\.local\bin`.

#### Exit Verification & Diagnostics

Upon completion, the uninstallation process outputs a status confirmation message strictly to `STDERR` (or terminal console):

```text
[cv-make] Uninstallation complete.
Container image purged and executable wrappers successfully removed.
```

## 3. Markdown-to-PDF Mapping & Formatting Engine

Section 3 specifies the internal transformation mechanics of the `cv-make` compilation engine. It details the multi-stage conversion pipeline—from raw Markdown AST parsing to semantic HTML DOM enrichment, cascading CSS style application, and final vector DTP rendering via WeasyPrint—ensuring visual precision and strict ATS semantic parseability.

### 3.1 Structural Parsing & Intermediate DOM Transformation

The conversion engine relies on a multi-pass Python preprocessor that ingests raw Markdown text from `STDIN` and transforms it into a fully enriched, semantic HTML5 Document Object Model (DOM) prior to rendering.

#### Multi-Stage Conversion Pipeline

The compilation workflow executes through five sequential transformation stages:

1. **AST Ingestion:** Reads the raw Markdown stream from `STDIN` and builds an Abstract Syntax Tree (AST) using `markdown-it-py`.
2. **Inline & List Formatting Mapping:** Standard Markdown syntax elements map directly to native HTML5 tags:
   * **Bold text (`**text**` / `__text__`):** Transformed into `<strong>text</strong>`.
   * **Italic text (`*text*` / `_text_`):** Transformed into `<em>text</em>`.
   * **Hyperlinks (`[label](url)`):** Transformed into `<a href="url">label</a>` URI annotations.
   * **Lists (Unordered & Ordered):** Single-level and nested bullet (`-`, `*`) and numbered (`1.`) lists map to `<ul class="cv-list">` and `<ol class="cv-list">` container structures with nested `<li>` elements, preserving structural indentation.
3. **Multi-Level Section Wrapping & DOM Enrichment:**
   * The preprocessor traverses the AST and wraps all structural content blocks under every heading level (H1, H2, H3, and H4) into semantic `<section>` containers.
   * Each `<section>` element is decorated with a `level-{n}` class, a `data-title` attribute containing the raw heading text, and an algorithmically generated slugified `id`:
      ```html
      <section class="cv-section level-2" id="work-experience" data-title="WORK EXPERIENCE">
         <h2>WORK EXPERIENCE</h2>
         ...
      </section>
      ```
   * **Slugification Algorithm:** Heading text is lowercased, non-alphanumeric characters are converted to hyphens (`-`), consecutive hyphens are collapsed (`--` -> `-`), and leading/trailing hyphens are trimmed.
4. **CSS Cascade & Stylesheet Link Injection:**
   * The preprocessor dynamically injects stylesheet references into the HTML `<head>`.
   * The embedded base stylesheet (`default.css`) is **always** linked first.
   * Custom stylesheets supplied via `--style` flags are linked sequentially immediately after `default.css`:
     ```html
     <head>
       <meta charset="UTF-8">
       <link rel="stylesheet" href="/app/styles/default.css">
       <link rel="stylesheet" href="/tmp/assets/style_00.css">
       <link rel="stylesheet" href="/tmp/assets/style_01.css">
     </head>
     ```
5. **DTP Rendering & Vector Emission:** The enriched DOM and resolved stylesheets are passed to WeasyPrint to produce a high-fidelity, ATS-compliant vector PDF emitted to `STDOUT`.

#### ATS Compatibility & Structural Integrity

* **Un-rasterized Text Layer:** Text content is preserved as vector glyph streams mapped to Unicode tables, guaranteeing 100% fidelity when processed by text extraction utilities (`pdftotext`).
* **Sequential DOM Order:** The HTML structure maintains a strictly logical reading flow. Visual layout enhancements (e.g., side-by-side date alignment) are achieved exclusively via CSS Flexbox styling, ensuring that automated ATS parsers read headings, contact details, and experience entries in their natural semantic order without text stream fragmentation.

### 3.3 Generic Pipe Splitter & Flex-Line Engine

To align employment periods, degree dates, and timeline metadata cleanly to the right margin, `cv-make` implements a universal, stateless line-splitting rule. In accordance with Requirement 6 & 7 and Requirement 10, the pipe symbol (`|`) is strictly reserved across all document sections as a layout divider, decoupling date extraction logic from specific section titles.

#### Parsing Rule & DOM Transformation Algorithm

During AST traversal, the preprocessor evaluates text nodes inside heading elements (`<h3>`, `<h4>`) and standalone paragraph elements (`<p>`):
1. **Pipe Detection:** The preprocessor checks if the line contains a pipe (`|`) symbol.
2. **Text Segment Splitting:** The line content is split at the pipe character into two distinct segments:
    * **Left Segment:** Contains the primary entity label (e.g., employer name, institution, or project title).
    * **Right Segment:** Contains the post-pipe text (e.g., date range or location), stripped of leading/trailing whitespace and the pipe character itself.
3. **Flex-Line Tag Ingestion:**
    * If the node is a heading (`<h3>` or `<h4>`), the preprocessor decorates the element with a `class="flex-line"` attribute and wraps the two segments into internal `<span>` wrappers:
        ```html
        <h3 class="flex-line">
          <span class="line-left">Acme Corporation</span>
          <span class="line-right">01.2023 – Present</span>
        </h3>
        ```
    * If the node is a standard paragraph (`<p>`), the preprocessor converts it into a flexbox container block:
        ```html
        <div class="flex-line">
          <span class="line-left">Project Alpha</span>
          <span class="line-right">2021 – 2022</span>
        </div>
        ```

#### Generic Input vs Output Examples

### 3.4 Heading Hierarchy & Typographic Density

In strict alignment with Requirement 10 (Minimal Structural Awareness), the conversion engine assigns no domain-specific semantic meaning (such as "historical experience" or "education") to heading levels. Instead, `cv-make` supports a fully generalized heading hierarchy from H1 through H6, delegating visual density, font scaling, and margin compression entirely to the CSS presentation layer.

#### Universal Hierarchy Mapping

The preprocessor parses Markdown headings (`#` through `######`) and encapsulates each structural block within nested or sequential HTML `<section>` containers:
* **H1 (`#`):** Document Primary Title (Candidate Name / Identity Header).
* **H2 (`##`):** Primary Document Sections (e.g., Profile, Experience, Skills, Education).
* **H3 (`###`):** Standard Subsection Entries (e.g., recent employment roles, university degrees).
* **H4 (`####`):** Compact Subsection Entries (e.g., condensed role summaries, project sub-items).
* **H5 / H6 (`#####` / `######`):** Deeply Nested / High-Density Details (e.g., granular skill groupings, publications, legacy entries).

Each heading level is automatically slugified and wrapped in accordance with Section 3.1:
```html
<section class="cv-section level-4" id="junior-developer-acme-corp" data-title="Junior Developer | Acme Corp">
  <h4>Junior Developer | Acme Corp</h4>
  <p>Software maintenance and bug fixing.</p>
</section>
```

Visual compression for deeper heading levels is driven purely by the CSS cascade. The base stylesheet (`default.css`) implements a progressive typographic scale where deeper section levels naturally inherit tighter margins, reduced line heights, and smaller font sizes:

The typography and visual formatting of the compiled PDF document are governed by CSS Paged Media specifications. `cv-make` decouples font assets and layout rules from the compilation engine, providing a robust default typographic theme while enabling full cascade overrides via custom user-supplied stylesheets.

#### Stylesheet Injection & Cascade Precedence

As specified in Requirement 1, Requirement 10, and Section 4.2, stylesheet resolution follows a strict cascade sequence:
1. **Base Stylesheet (`default.css`):** Built into the container image at `/app/styles/default.css`. It is **always** injected first into the intermediate HTML DOM `<head>`.
2. **User Stylesheet Append Chain:** For each custom CSS file path passed on the CLI via `--style` / `-s`, the host wrapper mounts the file and appends a corresponding `<link rel="stylesheet">` element to the DOM in exact invocation order:
    ```html

      <title>CV Document</title>

      <link rel="stylesheet" href="/tmp/assets/style_00.css">

    ```
3. **Cascade Evaluation:** WeasyPrint processes the linked stylesheets in sequential DOM order. Rules declared in user stylesheets naturally override base styles without requiring `!important` flags, giving users complete freedom to adjust colors, swap font families, modify margins, or customize bullet list styles.

#### ATS Compatibility & Vector Text Validation

* **Searchable Text Stream:** The rendered PDF contains a clean, un-rasterized text stream. The structural order of HTML elements ensures that copying text or running `pdftotext input.pdf output.txt` produces clean, un-mangled text.
* **Clickable Hyperlinks:** All `<a>` tags with valid `href` attributes are rendered as interactive PDF annotations, allowing ATS engines and human recruiters to navigate directly to external URLs (LinkedIn, GitHub, portfolio sites).

## 4. Architecture, Containerization & CI/CD Pipeline

### 4.1 System Architecture & Tech Stack

The architecture of `cv-make` is designed around component isolation, minimal host dependencies, and strict compilation reproducibility. The system is split into two primary layers: a lightweight, host-level orchestration layer (the executable wrapper scripts) and an encapsulated containerized execution environment housing the document processing stack.

#### Base OS & Container Runtime Rationale

* **Base Image:** `debian:trixie-slim` (Debian 13 Trixie, minimal variant).
* **Selection Rationale:**
    * **Stability & Security:** Provides a minimal, well-maintained base operating system with up-to-date security patches.
    * **Native DTP Dependencies:** Simplifies installation of WeasyPrint runtime dependencies (Pango, GdkPixbuf, cairo, libffi) and system fonts directly through `apt-get` without compiling heavy C libraries from source.
    * **System Font Management:** Provides standard, DFSG-compliant system font packages (such as `fonts-ibm-plex`), ensuring fonts are managed directly by the container's package manager.

#### Application Tech Stack & Component Roles

The containerized document processing engine relies on a lightweight Python 3 stack:

1. **Python 3 Runtime:** Serves as the primary orchestration runtime inside the container, executing `/app/cv_make.py`.
2. **`markdown-it-py` (Markdown AST Parser):** Ingests raw Markdown text from `STDIN` and generates an Abstract Syntax Tree (AST). It provides fast, CommonMark-compliant parsing with extensible AST token handling.
3. **`BeautifulSoup4` (HTML DOM Transformation Engine):** Inspects and manipulates the intermediate HTML structure. It performs section wrapping (`<section class="cv-section level-{n}" id="{slug}">`), multi-level slugification, and pipe-splitting (`<h3 class="flex-line">`) transformation.
4. **`Jinja2` (HTML Document Templating):** Renders the final, standalone HTML5 document structure, dynamically injecting page titles, viewport meta tags, and ordered `<link rel="stylesheet">` tags into the `<head>` block.
5. **`WeasyPrint` (DTP Rendering Engine):** Converts the enriched HTML5 DOM and cascading CSS stylesheets into a publication-ready PDF document. WeasyPrint supports CSS Paged Media standards (`@page`), vector text embedding, and interactive PDF hyperlink annotations.

### 4.2 Wrapper Execution Architecture & Streaming Mechanics

To enforce strict execution isolation and eliminate file permission conflicts across host operating systems, `cv-make` establishes a decoupled, stream-oriented architecture between the host wrapper script and the container runtime environment.

#### System Execution & Data Flow Architecture

The following diagram illustrates the complete operational boundary separation, streaming pipeline, volume mounting strategy, and internal execution sequence.

#### Streaming Protocol Specifications

The containerized preprocessor operates exclusively in a pure stream-processing mode for document content:

1. **Input Stream Ingestion (`STDIN`):** The preprocessor inside the container reads raw Markdown source text directly from `sys.stdin`. The Python script remains agnostic as to whether the host wrapper read a file path or forwarded a live pipe.
2. **Output Stream Emission (`STDOUT`):** The compiled binary PDF document is written directly to `sys.stdout.buffer`.
3. **Diagnostic Stream Isolation (`STDERR`):** All progress indicators, container auto-detection notices, warnings, and error messages are written exclusively to `sys.stderr`. Writing text logs to `STDOUT` is strictly prohibited to prevent PDF binary corruption.

#### Asset Mounting & Path Translation Protocol

To guarantee least-privilege security and eliminate file permission issues (e.g., UID/GID rootless mapping conflicts on Linux):

* The wrapper resolves absolute host paths for optional assets (`--photo` and `--style`).
* Each asset file is mounted individually as a read-only volume (`-v "/host/file:/tmp/assets/target:ro,z"`) into an isolated `/tmp/assets/` directory within the container.
* The container wrapper never mounts the host's entire working directory (`pwd`), preventing unintended container access to host files.

#### Custom Stylesheet Ingestion & Cascade Ordering

Preserving the exact user-intended CSS cascade order across multiple `--style` flag invocations is guaranteed through a 4-step execution chain:

1. **Host CLI Evaluation:** The host wrapper parses command-line arguments sequentially from left to right.
2. **Indexed Mount Mapping:** For each `--style` (or `-s`) flag encountered, the wrapper assigns a zero-padded index (e.g., `style_00.css`, `style_01.css`) and mounts the file into `/tmp/assets/`.
3. **Ordered Argument Array Construction:** The wrapper constructs the container execution command, appending repeated `--style` options in the exact sequence they were supplied on the host CLI:
`--style /tmp/assets/style_00.css --style /tmp/assets/style_01.css`
4. **HTML Link Injection & Cascade Execution:** Inside the container, Python's `argparse` module (`action='append'`) collects the paths into an ordered list. The preprocessor injects corresponding `<link rel="stylesheet">` elements into the DOM `<head>` sequentially after the base `default.css`:
    ```html
    <link rel="stylesheet" href="/app/styles/default.css">
    <link rel="stylesheet" href="/tmp/assets/style_00.css">
    <link rel="stylesheet" href="/tmp/assets/style_01.css">
    ```

WeasyPrint evaluates the stylesheets in this exact DOM order, ensuring standard CSS specificity and override behavior.

#### Architectural Benefits

* **Zero Host File Pollution:** The container operates as a read-only sandbox regarding host filesystems, writing solely to stdout.
* **Path Separation:** The Python runtime handles container-internal POSIX paths (`/tmp/assets/`), freeing the application from handling Windows vs POSIX path separator translation.
* **Deterministic Pipeline Integration:** `cv-make` seamlessly operates within standard Unix pipelines (`cat CV.md | cv-make --photo photo.jpg > cv.pdf`).

### 4.3 Container Image Specification (`Dockerfile`)

The container image serves as the immutable runtime environment for `cv-make`. Built upon `debian:trixie-slim`, it encapsulates the Python 3 interpreter, system fonts (`fonts-ibm-plex`), DTP layout libraries (Pango, Cairo, GdkPixbuf), and Python parsing dependencies (`markdown-it-py`, `beautifulsoup4`, `jinja2`, `weasyprint`).

The image build specification is named **`Dockerfile`**. * `/app/`: Application root directory housing source scripts and base assets.

```dockerfile
    libpangoft2-1.0-0 \
    libgdk-pixbuf-2.0-0 \
    libffi-dev \
    shared-mime-info \
    && rm -rf /var/lib/apt/lists/*

# Create virtual environment and install Python dependencies
RUN python3 -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"

RUN pip install --no-cache-dir \
    markdown-it-py \
    beautifulsoup4 \
    jinja2 \
    weasyprint

# Set working directory for application binaries
WORKDIR /app

# Copy application source files and default stylesheet
COPY cv_make.py /app/cv_make.py
COPY styles/default.css /app/styles/default.css

# Prepare asset mount directory with appropriate permissions
RUN mkdir -p /tmp/assets && chmod 777 /tmp/assets

# Set entrypoint to run the Python preprocessor
ENTRYPOINT ["python3", "/app/cv_make.py"]
```

#### Optimization & Security Parameters

1. **Minimal Layer Footprint:** System packages are installed in a single `RUN` instruction combined with `rm -rf /var/lib/apt/lists/*` to eliminate temporary package caches, keeping the image size low.
2. **Virtual Environment Isolation:** Python dependencies are compiled inside an isolated virtual environment (`/opt/venv`), avoiding conflicts with Debian system Python packages.
3. **Rootless Execution Compatibility:** The container entrypoint executes without requiring root privileges or file-write permissions on the host, ensuring safe rootless execution under Podman and Docker.

### 4.4 GitHub CI/CD & Distribution via GHCR

To guarantee automated, repeatable builds and effortless software distribution, `cv-make` leverages GitHub Actions and the GitHub Container Registry (GHCR). Whenever source code updates are merged or new release tags are created, the CI/CD pipeline automatically builds, verifies, and publishes container images to `ghcr.io`.

#### Distribution Model & Registry Namespace

* **Target Registry:** GitHub Container Registry (`ghcr.io`).
* **Image Namespace:** `ghcr.io/<owner>/cv-make`.
* **Public Visibility:** The GHCR package visibility is configured as **Public**. This allows end-users to execute unauthenticated container pulls (`podman pull ghcr.io/<owner>/cv-make:latest` or `docker pull`) during installation and runtime self-healing without requiring `docker login` or GitHub Personal Access Tokens (PATs).

#### Automated Multi-Tagging Strategy

The workflow enforces a multi-tagging convention based on Git references to support both stability and continuous delivery:

1. **`latest` Tag:** Automatically updated on every push to the `main` default branch and on every published release tag. Ensures that default installations always receive the most up-to-date stable build.
2. **Semantic Version Tags (`vX.Y.Z`, `vX.Y`, `vX`):** Triggered upon pushing Git tags matching the `v*.*.*` pattern (e.g., `v1.0.0`). The workflow generates granular version tags (`1.0.0`, `1.0`, `1`), allowing users to lock onto specific major or minor release channels.
3. **Git Commit SHA (`sha-XXXXXXX`):** Generates an immutable, traceable tag corresponding to the short Git commit hash, aiding auditability and regression testing.

#### GitHub Actions Workflow Specification (`.github/workflows/release.yml`)

The build and publication process is defined in `.github/workflows/release.yml`:

```yaml
name: Build and Publish Container Image

on:
  push:
    branches:
      - main
    tags:
      - 'v*.*.*'
  workflow_dispatch:

permissions:
  contents: read
  packages: write

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Log in to GitHub Container Registry
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Extract Metadata & Generate Tags
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=raw,value=latest,enable=${{ github.ref == 'refs/heads/main' || startsWith(github.ref, 'refs/tags/v') }}
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
            type=semver,pattern={{major}}
            type=sha,prefix=sha-,format=short

      - name: Build and Push Image
        uses: docker/build-push-action@v5
        with:
          context: .
          file: ./Dockerfile
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

#### Security & Access Control

* **Zero Secrets Leakage:** The workflow utilizes the ephemeral, auto-generated `${{ secrets.GITHUB_TOKEN }}` provided natively by GitHub Actions. No long-lived personal access tokens or credentials are stored in repository secrets.
* **Least-Privilege Permissions:** Permissions are strictly scoped at the job level to `contents: read` (for checking out source code) and `packages: write` (for publishing container images to GHCR).
* **Layer Caching Optimization:** Build layers are cached using GitHub Actions Cache (`type=gha`), reducing build times for subsequent pipeline executions.

### 4.5 Local Development & Testing Workflow

Section 4.5 outlines the development, local execution, and Quality Assurance (QA) testing workflows for contributors working on the `cv-make` codebase. It provides explicit guidelines for rapid local iteration, source code mounting without container rebuilds, and ATS compliance validation.

#### Local Development Environments

Developers are encouraged to use **Podman** as their primary container engine during local development, particularly on Linux (Debian 13 Trixie) or Windows 10/11 environments running PowerShell 5.1+.

#### Rapid Iteration Cycle (Hot Source Mounting)

When modifying the preprocessor Python script (`cv_make.py`) or the base stylesheet (`styles/default.css`), developers can test changes instantly without triggering time-consuming container rebuilds (`podman build`).

1. **Local Dev Container Build:**
    Build a local development image tagged as `cv-make:dev`:
    ```bash
    podman build -t cv-make:dev .
    ```
2. **Source-Mounted Execution:**
    Mount local development files directly over the container's `/app` directory in read-only mode to execute live code changes instantly:
    ```bash
    podman run -i --rm \
      -v "$(pwd)/cv_make.py:/app/cv_make.py:ro,z" \
      -v "$(pwd)/styles/default.css:/app/styles/default.css:ro,z" \
      -v "$(pwd)/sample_photo.jpg:/tmp/assets/photo.jpg:ro,z" \
      cv-make:dev --photo /tmp/assets/photo.jpg < CV.md > output_test.pdf
    ```

#### Manual CV Generation Validation Protocol

Before submitting code changes or tagging a new release, developers must execute a three-step validation suite:

1. **Visual Layout & Pagination Inspection:**
    * Verify page boundaries and check that `@page` margins prevent orphan headings.
    * Ensure header elements, contact metadata, and photograph render symmetrically.
    * Confirm right-aligned date blocks (`.flex-line`) align flush to the right page margin.
2. **ATS Text Extraction Check (`pdftotext`):**
    Execute `pdftotext` to confirm that the generated PDF preserves a clean Unicode text stream without scrambled glyphs or missing section headers:
    ```bash
    pdftotext output_test.pdf - | head -n 40
    ```
    *Expected Result:* Clean, human-readable plain text matching the logical Markdown reading order.
3. **Hyperlink & Navigation Audit:**
    * Inspect interactive URI annotations for email addresses (`mailto:`), LinkedIn profiles, and GitHub repositories using a standard PDF viewer.
    * Confirm all links remain clickable and visually highlighted without breaking layout geometry.
